## 1. 硬冲突（按方案实施会写出与定案不符的实现）

### DB01 · 认证选型二选一残留（Spring Security 未砍）
- **位置**：§6.1 后端清单第 5 条（L127）；§6.3 认证流程第 3 步（L159）
- **原文**：`- Spring Security 或 自定义拦截器 + JWT（jjwt 库）`；`3. 后端拦截器/过滤器统一校验 Token 合法性与有效期，解析出用户信息放入上下文（ThreadLocal）；`
- **定案**：[SRS §8](docs/SRS.md)（L288）「JWT 认证 = **自定义拦截器 + jjwt**：HandlerInterceptor 校验 Token → 解析用户入 ThreadLocal → 路径级角色判断（管理端校验 role = ADMIN）。**不采用 Spring Security**」；[hld §1.1 决策 1](docs/hld.md)（L20）；[GDD §0.3](docs/gdd.md)（L43）
- **裁决**：改方案为唯一写法「自定义拦截器（HandlerInterceptor）+ jjwt」；L159 的「拦截器/过滤器」同步收敛为「拦截器」。
- **理由**：认证选型是 hld 技能矩阵与权限三档（§4.2）实现的地基；留着「或 Spring Security」，按方案建工程就会引 Security 全家桶，与 SRS §8 唯一定案项直接冲突。**方案自身已矛盾**：§五 非功能表 L104 写的是 `JWT + 拦截器`，与 §6.1 打架（附注 A-1）。

### DB02 · 图片存储 OSS 分支未砍
- **位置**：§6.1 L130；§6.2 分层架构图 L151
- **原文**：`- 本地磁盘存储或阿里云 OSS（图片上传）`；`│  本地/OSS（图片文件）`
- **定案**：[FSR §4.1](docs/FSR.md)（L71）「本地磁盘存储（**不引 OSS，断网可答辩演示**）」；[SRS §2.2 图片规则](docs/SRS.md)（L82）；[GDD §0.4](docs/gdd.md)（L50）；[hld §1.1 决策 6](docs/hld.md)（L25）+ §1.2（L47）
- **裁决**：删 OSS 分支，改「本地磁盘存储（不引 OSS）」，架构图 L151 同步为「本地磁盘（图片文件）」。
- **理由**：经济可行性（¥0 基线）与「断网可演示」两条判据都挂在这句上（FSR §4.1 / §9 风险矩阵「答辩演示环境故障」）；OSS 分支留着等于留了一条带成本与联网依赖的实施路径。

### DB03 · 「核心表清单（10 张）」与 report 表选做
- **位置**：§7.2 标题 L178；report 行 L191
- **原文**：`### 7.2 核心表清单（10 张）`；`| report | 举报表（选做） | id, user_id, target_id, target_type, reason, status |`
- **定案**：[hld §3.2](docs/hld.md)（L162）「P0 建表 **9 张**：user / destination / article / tag / article_tag / comment / like_record / collect_record / carousel。**report（举报）表不建**（FSR §7 P2 排除）」；hld §3.2 剪裁 4（L169）「`/api/report/**` 不进入 §4.2 权限档表，实施期不为其留桩」；[FSR §7 P2](docs/FSR.md)（L114）
- **裁决**：标题改「核心表清单（P0 九张）」；report 行移出清单（或留在文末但标「P2 排除，不建」）。
- **理由**：表清单差一字即建表脚本差一张表；这同时是 hld §3.2 剪裁的验收依据，留着 10 张会让 hld 定案项自证矛盾。

### DB04 · 「攻略四状态」两处（应为五态八条边）
- **位置**：§四「审核策略建议」L97；§九 亮点 1 L236
- **原文**：`（攻略有 draft/pending/approved/rejected 四种状态，仅 approved 对前台可见）`；`攻略四状态流转 + 驳回理由`
- **定案**：[SRS §1.3](docs/SRS.md)（L30 起）「攻略生命周期**五态**（article.status）：0 草稿 / 1 待审 / 2 通过 / 3 驳回 / 4 下架」+ 八条边全集表；[GDD §0.1](docs/gdd.md)（L17 起）；[GLOSSARY「攻略五态」](GLOSSARY.md)（L9–11）「_Avoid_: **四态**（历史叫法，含下架后实为五态）」；[hld §1.1 决策 2](docs/hld.md)（L21）
- **裁决**：两处改「五态八条边」并挂 SRS §1.3 指针；L97 整段由「策略建议（先发后审 vs 先审后发，推荐后者）」改写为「已定案：先审后发」+ 补下架态。
- **理由**：GLOSSARY 已把「四态」列为 Avoid 词；这是论文第五章与答辩讲状态机时会直接抄的一句。L97 的「建议二选一」口吻也与「已批复定案」不符。

### DB05 · 「攻略与评论均可点赞」
- **位置**：§3.3 互动模块 L73
- **原文**：`| 点赞 / 取消点赞 | 攻略与评论均可点赞，需防重复（数据库唯一索引） | 核心必做 |`
- **定案**：[FSR §7 偏离声明](docs/FSR.md)（L118）「方案 §3.3「攻略与评论均可点赞」中的评论点赞，经 SRS 问询定案砍除（点赞对象 = 攻略；方案 §7.2 点赞表与 §8.2 点赞接口设计不变）」；[SRS §2.3](docs/SRS.md)（L93）；[GDD FR-ACT-03](docs/gdd.md)（L188）「评论不做点赞」
- **裁决**：§3.3 改「攻略点赞 / 取消点赞（评论不做点赞）」；§7.2 点赞表与 §8.2 点赞接口保持原样（FSR 已明确这两处不变）。
- **理由**：**方案自身不可实现**——§7.2 like_record 只有 user_id, article_id（L188），无 target 区分，评论点赞无处落（附注 A-2）。这是 FSR 唯一一条正面偏离声明，留着会让范围纪律失效。

### DB06 · 逻辑删除被写成全域规则
- **位置**：§7.3 设计原则 L196
- **原文**：`- 采用**逻辑删除**（deleted 字段）而非物理删除，便于数据恢复与统计；`
- **定案**：[hld §3.2 剪裁 2](docs/hld.md)（L167）「like_record / collect_record **不设逻辑删除旗标**：「取消」即删除关联行——user_id + article_id 唯一索引才能持续防重（取消后可再赞）。这两张表是**全部业务表中仅有的两张行级删除表**」；剪裁 3（L168）「article_tag 关联行随攻略保存整体重建」；[GDD §0.1 补充 6](docs/gdd.md)（L24）；[GDD §0.6](docs/gdd.md)（L65）
- **裁决**：把规则限定作用域——① 业务实体表（user / destination / article / tag / comment / carousel）逻辑删；② like_record / collect_record 取消即**物理删行**；③ article_tag 随攻略保存整体重建、行无逻辑删语义。
- **理由**：这是能**直接写坏代码**的一条：给两张互动表加 deleted，唯一索引防重立刻失效（取消后再赞必撞唯一键），FR-ACT-01/02 的验收判据全废。

### DB07 · 审核状态机排期错位（P0 被排进 P1 时间盒）
- **位置**：§10.1 16 周进度表 L253（兼 §九 亮点 1 L236）
- **原文**：`| 亮点开发 | 第 11–12 周 | 审核状态机、标签推荐、缓存（按选做清单） |`
- **定案**：[FSR §7 P0](docs/FSR.md)（L112）「P0 承诺范围 = 方案 §三 / §四表中全部「核心必做」项 + 先审后发（五态）审核状态机」；[FSR §6](docs/FSR.md)（L98 / L100–104）「第 5–10 周核心开发 → 第 11–12 周 **P1 时间盒**；**CP2 核心闭环（第 10 周末）P0 全部可演示**」；[SRS §1.4](docs/SRS.md)（L55）「§2–§3 全部为 P0」+ FR-AUDIT-01 在 §3
- **裁决**：§10.1 第 11–12 周行删「审核状态机」（只留 标签推荐 / Redis 缓存 / 数据分析）；第 5–10 周行补「含审核状态机与后台治理」；§九 亮点 1 改标「已升 P0 核心（FSR §7）」，亮点位改讲状态机作为论文叙事的加分点（不是范围）。
- **理由**：按方案排期，第 10 周末 CP2 判据**不成立**（状态机是 P0，缺一即闭环不成立），会连带推翻 FSR §6 的 16 周进度可行性结论。这是 map「Not yet specified」点名要对的「16 周进度安排对齐」——已收口，结论是方案排期错位，而非 FSR 排期错。

### DB08 · 人均花费字段类型二选一残留
- **位置**：§7.3 L199
- **原文**：`- 金额类字段（cost）用 DECIMAL 或整型（元），不用 FLOAT；状态字段用 TINYINT；`
- **定案**：[GDD FR-ART-01 字段规则表](docs/gdd.md)（L135）「人均花费 | 可选 **0–999,999 整数（元）**」
- **裁决**：方案改单一写法「cost 用整型（元），范围 0–999,999」，删「或 DECIMAL」。
- **理由**：二选一会直接分叉到接口与前端控件（DECIMAL → 小数输入 / BigDecimal 序列化；整型 → 整数输入），GDD 已定整数，这里是字段明细事实源漏收敛。

## 2. 字段与库表缺口（§7.2 是字段明细唯一事实源，漏列 = 按方案建表会漏列）

### GP01 · user 表缺「简介」列
- **位置**：§7.2 user 行 L182
- **原文**：`| user | 用户表 | id, username, password(BCrypt), nickname, avatar, role(USER/ADMIN), status, create_time |`
- **定案**：[GDD FR-USER-03](docs/gdd.md)（L88）「简介（**≤200 字符**）」为必做字段；[SRS FR-USER-03](docs/SRS.md)（L66）「修改昵称、头像、简介、密码」
- **裁决**：user 表补 `intro varchar(200)`。
- **理由**：不补则建表漏列，FR-USER-03 与个人信息接口无法验收；方案是字段明细唯一事实源，SRS/GDD 只写需求不写列。

### GP02 · article 表缺 content_text（纯文本副本）
- **位置**：§7.2 article 行 L184
- **原文**：`| article | 攻略表 | id, user_id, destination_id, title, content(富文本), cover_img, days, cost, view_count, like_count, collect_count, comment_count, status(0草稿/1待审/2通过/3驳回/4下架), reject_reason, create_time |`
- **定案**：[GDD §6.2 库表增量](docs/gdd.md)（L274）「article 表增加 content_text（纯文本副本）列」；[GDD FR-ART-01](docs/gdd.md)（L136）+ [FR-ART-03](docs/gdd.md)（L150）；[hld §3.1 E-R](docs/hld.md)（L125–126）
- **裁决**：article 补 `content_text`。
- **理由**：搜索 LIKE 的对象是它而非富文本原文；漏列则实现会退化成 LIKE 富文本，搜「span」误中 HTML 标记——FR-ART-03 的验收判据直接失败。

### GP03 · carousel.link 无形态定义（与「对象选择器」定案不落）
- **位置**：§7.2 carousel 行 L190
- **原文**：`| carousel | 轮播图表 | id, img_url, link, sort, status |`
- **定案**：[GDD FR-ADMIN-CAR-01](docs/gdd.md)（L262）「**link = 后台动作的可执行对象选择器**：类型（攻略/目的地）+ 对象二选一，**不做自由文本外链**。失败路径：非选择器形态的 link → 表单不允许提交」；[GLOSSARY「后台动作的可执行对象选择器」](GLOSSARY.md)（L99–101）
- **裁决**：carousel 改 `target_type(ARTICLE/DESTINATION)` + `target_id`（若坚持单列 link，必须写清它只承载类型化引用，不得存外链 URL）。
- **理由**：单列 link 不带类型信息，GDD 已把语义定成「选择器 + 二选一对象」，表单校验、点击跳转与后台维护三处都依赖这个形态；不改则最省事的做法就是存外链字符串，与定案冲突。

### GP04 · comment.parent_id 标「选做」而非「建表即含」
- **位置**：§7.2 comment 行 L187
- **原文**：`| comment | 评论表 | id, article_id, user_id, content, parent_id(选做二级评论), create_time |`
- **定案**：[hld §3.2 剪裁 1](docs/hld.md)（L166）「comment.parent_id **建表即含，P0 恒空**：一级评论不写入该列；P1 二级评论免 ALTER 迁移」
- **裁决**：方案改「parent_id（P1 预留，P0 恒空，**建表即含**）」。
- **理由**：「选做」的自然读法是「先不建这列」，正是 hld 剪裁要避免的那条 P1 ALTER 迁移。

## 4. 表述精度不足（不导致错误实现，但影响实施口径与答辩叙事）

### PR01 · 「收藏夹式管理」暗示多夹模型
- **位置**：§3.3 L74 · **原文**：`| 收藏 / 取消收藏 | 收藏夹式管理 | 核心必做 |`
- **定案**：[GDD FR-USER-05](docs/gdd.md)（L112–115）三 Tab（我的收藏 / 点赞 / 评论记录）各自分页；[GDD §0.6](docs/gdd.md)（L67）「三列表只显示前台可见的攻略…不做灰显徽标」
- **裁决**：改「个人中心「我的收藏」单一列表 Tab」。**理由**：「收藏夹」= 多夹分组（要建夹表 + 归属关系），GDD 定的是单列表聚合；不回收会被当 P0 隐含功能实现。

### PR02 · §8.1 只给成功响应示例，无错误约定
- **位置**：§8.1 L209 · **原文**：`{ "code": 200, "message": "success", "data": { } }`
- **定案**：[GDD §0.2](docs/gdd.md)（L28–39）「HTTP 状态码对齐，body 恒为 {code, message, data} 且 **code 与 HTTP 状态码一致**」+ 400/401/403/404/500 场景表 + Axios 分发
- **裁决**：§8.1 补一行指针「错误码与 HTTP 状态映射 → GDD §0.2」（**不复制规则**）。**理由**：方案是接口明细事实源却只示范成功体，实施者极易自造 code 体系（0/200 混用），直接违反 GDD 定案。

### PR03 · CORS 备选叙述与「代理/反代」定案并存
- **位置**：§6.4 L166 · **原文**：`…同样规避跨域（也可在后端配置 CORS 作为备选，论文中可对比两种方案）。`
- **定案**：[hld §1.1 决策 9](docs/hld.md)（L28）「开发 Vite 代理 `/api` → 8080；生产 Nginx 反代同前缀」；方案同段前半已与之一致
- **裁决**：保留「论文可对比」的叙事，但加「**P0 不配置 CORS**」。**理由**：否则实施期可能为了「论文对比两种方案」真开后端 CORS，与 hld 代理定案形成两套跨域口径。

### PR04 · §十一 数据分析模块未标 P1
- **位置**：§十一 L273 · **原文**：`在后台数据看板基础上扩展为独立的"平台数据分析"模块，全部基于 MySQL 聚合查询 + Redis 缓存…`
- **定案**：[SRS §6](docs/SRS.md)（L274）数据分析模块 = P1（CP2 通过 + 第 11–12 周时间盒）；[FSR §7 P1](docs/FSR.md)（L113）；[hld §5](docs/hld.md)（L208）「数据分析模块设计（P1 实施才写）」
- **裁决**：§十一 抬头加「**P1 条件增强（FSR §7 / SRS §6）**」。**理由**：P0 看板只有四项指标（FR-BOARD-01），方案写成「扩展为独立模块」读感像 P0 增量，会挤压第 5–10 周。
